# 공방 제작/건설 대기열 기획서

작성일: 2026-03-08  
연관 시스템: 킹덤 건설, 생산 건물, 재화 소모/획득, 시간 단축

## 1. 목표
- 공방/생산 건물의 제작과 건설을 "대기열"로 관리한다.
- 플레이어는 제작 예약, 취소, 즉시 완료(가속), 보상 수령을 일관된 규칙으로 사용한다.
- 중복 클릭/재접속/서버 재시작 상황에서도 결과가 꼬이지 않게 만든다.

## 2. 게임 플레이 콘셉트
- 대상 건물:
1. 뚝딱 대장간
2. 나무꾼의 집
3. 제과 공방
- 플레이 흐름:
1. 레시피 선택 후 제작 시작
2. 대기열에 작업이 쌓임
3. 건물 슬롯이 비면 순서대로 진행
4. 완료 후 창고 적재 또는 직접 수령
5. 필요하면 취소/가속 사용

## 3. 핵심 규칙

## 3.1 대기열 규칙
- 건물마다 동시 제작 가능한 슬롯 수가 다르다.
- 기본 순서는 먼저 넣은 작업부터 처리(FIFO).
- 긴급 제작권이 있으면 우선 순위를 올릴 수 있다.

## 3.2 시간 규칙
- 모든 진행 시간은 서버 시간을 기준으로 계산한다.
- 클라이언트 시간은 표시용이다.
- 오프라인 중에도 시간이 흐른 것으로 계산한다.

## 3.3 취소/가속 규칙
- 취소:
1. 시작 전 작업은 전액 환급
2. 진행 중 작업은 일부 환급(기획 수치)
- 가속:
1. 남은 시간에 따라 비용 계산
2. 보석/가속권으로 즉시 완료 가능

## 3.4 보상 수령 규칙
- 완료 작업은 수령 전까지 "완료 보관함" 상태로 유지한다.
- `일괄 수령` 지원
- 같은 작업을 두 번 수령할 수 없게 차단한다.

## 4. 상태 단계
- `예약됨` -> `진행중` -> `완료` -> `수령완료`
- 예외 상태:
1. `취소됨`
2. `만료됨`(이벤트성 제작 등 기간 제한 시)

## 5. 서버 처리 개요
- 서버는 다음을 보장한다.
1. 제작 시작 요청의 중복 처리 방지
2. 완료 판정의 정확성
3. 보상 지급의 1회성 보장
- 내부적으로는 스케줄러 워커가 완료 시점을 주기적으로 확인한다.

## 6. 데이터 모델(초안)

## 6.1 MySQL
- `KingdomCraftJob`
1. `JobId`
2. `PlayerId`
3. `BuildingId`
4. `RecipeNum`
5. `State`
6. `StartAt`
7. `EndAt`
8. `ClaimedAt`
9. `RequestKey` (중복 요청 방지 키)
- `KingdomCraftCostLog`
1. `JobId`
2. `ObjType`
3. `ObjNum`
4. `Amount`
5. `Reason`
- `KingdomCraftRewardLog`
1. `JobId`
2. `ObjType`
3. `ObjNum`
4. `Amount`
5. `ClaimTxId`

## 6.2 Redis(선택)
- `kingdom:craft:due` (완료 시각 기준 정렬)
- `kingdom:player:{playerId}:jobs` (빠른 목록 조회)
- `lock:kingdom:craft:{jobId}` (중복 처리 방지)

## 7. API/RPC 초안

- `kingdom/craft/list`
- `kingdom/craft/cancel`
- `kingdom/craft/speedup`
- `kingdom/craft/claim`
- `kingdom/craft/claim-all`

## 8. 클라이언트 UX 요구사항
- 건물별 대기열 UI(남은 시간, 순번, 슬롯 상태)
- 완료 알림 배지
- 일괄 수령 버튼
- 취소/가속 시 예상 비용 사전 표시

## 9. 예외/장애 대응
- 중복 클릭:
1. 동일 요청 키는 같은 결과 반환
- 서버 재시작:
1. 재기동 시 진행중 작업을 서버 시간 기준으로 재계산
- 네트워크 재시도:
1. 요청 키로 중복 지급 방지

## 10. 운영 지표
- 작업 생성 수/완료 수/수령 수
- 평균 제작 대기 시간
- 가속 사용률
- 중복 수령 차단 횟수
- 오류 및 롤백 횟수

## 11. 개발 단계
1. P1: 단일 건물 제작 시작/완료/수령
2. P2: 취소/가속/일괄 수령
3. P3: 다중 건물 대기열 + 복구 처리 + 운영 지표
